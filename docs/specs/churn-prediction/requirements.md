## 1. 專案目標與目標讀者

### 1.1 要解決的問題
電信公司留住舊客戶的成本遠低於開發新客戶，但客服與行銷人員不知道「哪些客戶快要離開」。本專案用歷史資料訓練模型，讓使用者輸入一位顧客的資料，就能得到「這位顧客有多可能流失」、「為什麼」，以及「這個模型到底準不準」。

### 1.2 專案真正的目的
這是面試用作品集。除了「模型能預測」，更要讓面試官在 5 分鐘內看出：
1. 懂機器學習流程（資料清理、類別不平衡、基準模型比較、用對指標、誠實揭露限制）。
2. 能把模型做成完整、可執行、可維護的產品（前後端分離、API 文件、測試、CI、Docker、決策紀錄）。

不做這個專案會怎樣：作品集缺少「ML 加完整 Web App」的代表作，面試時只能口述，無法現場展示。

### 1.3 目標讀者
| 讀者 | 想從專案得到什麼 |
|---|---|
| 面試官（主要） | 打開 README 與線上操作 demo，快速判斷技術深度與工程素養 |
| 使用者本人 | 面試時能流暢講解每個設計取捨 |
| 之後 clone 專案的開發者 | 一個指令跑起來、看得懂架構 |

## 3. 資料說明（資料來源與量級）

- 來源：Kaggle「Telco Customer Churn」（IBM 範例資料），檔名 `WA_Fn-UseC_-Telco-Customer-Churn.csv`，約 7,043 筆、21 欄。
- 放置位置：由使用者自行下載後放到 `data/raw/`；資料尚未下載。
- 目標欄位：`Churn`（Yes/No），約 26.5% 為 Yes（類別不平衡）。
- 已知問題：`TotalCharges` 有少數空白字串（依公開資訊約 11 筆，且多為 tenure 為 0 的新客戶，需以實際資料確認）。
- `customerID` 只是識別碼，不可當作預測特徵。
- 個資：此為公開的虛構範例資料，不含真實個人資訊；本系統不儲存使用者輸入或上傳的資料（MVP 不做預測紀錄）。
- 資料是否進版控：原始 CSV 不放進程式庫（README 寫明下載方式）；CI 用一份小型測試樣本，不依賴完整資料。

### 4.2 之後再做（未來可擴充）
- 預測歷史紀錄（需引入 PostgreSQL）。
- 全體資料的整體特徵重要性分析頁。
- 第三個模型比較（隨機森林或 XGBoost 等樹模型），用來呈現「表格資料樹模型常更強」的見解（Q6 決定）。
- 模型版本管理與多模型切換。
- What-if 情境模擬（調整合約類型，看機率如何變化）。
- 雲端部署（含公開網址）。
- 英文介面（i18n）。

### 4.3 明確不做
見第 8 節。

### 4.4 為什麼不用 PostgreSQL（本次判斷）
MVP 的資料都是「唯讀」的：訓練資料是 CSV、模型與成效指標是訓練後產生的檔案、預測是即時計算不需留存。沒有任何需要「新增、查詢、修改」的資料，加資料庫只會增加啟動複雜度，且面試官一看就知道是為用而用。故 MVP 不使用資料庫。只有在做「預測歷史紀錄」時才引入，屆時以 ADR 記錄這個決定。

## 5. 使用者故事與驗收標準

驗收標準格式為 Given / When / Then，編號 AC-x.y，QA 直接依此測試。

### F1 單筆顧客流失預測

**US-1** 身為留客分析人員，我想要輸入一位顧客的基本資料與使用服務，以便立刻知道他流失的機率與風險等級，決定要不要優先關懷。

輸入欄位（共 19 個，對應資料欄位，排除 customerID 與 Churn）：gender、SeniorCitizen、Partner、Dependents、tenure、PhoneService、MultipleLines、InternetService、OnlineSecurity、OnlineBackup、DeviceProtection、TechSupport、StreamingTV、StreamingMovies、Contract、PaperlessBilling、PaymentMethod、MonthlyCharges，以及選填的 TotalCharges（Q3 決定：18 個必填欄位加 1 個選填欄位；沒填時系統以 tenure x MonthlyCharges 估算，並在畫面註明為估算值）。

風險等級切點（預設，見待確認 Q2）：機率 < 30% 為「低」、30% 至 < 60% 為「中」、>= 60% 為「高」。

| 編號 | Given | When | Then |
|---|---|---|---|
| AC-1.1（C Q3 修改） | 開啟預測頁 | 頁面載入完成 | 顯示 19 個輸入欄位，其中 18 個標示為必填、TotalCharges 標示為「選填」並附說明「未填時以在網月數 x 月費估算」；類別欄位用下拉或單選，選項與資料集的合法值完全一致；每個欄位有中文標籤 |
| AC-1.2 | 填入一組合法資料 | 按「預測」 | 顯示流失機率（百分比，小數 1 位）與風險等級（低／中／高，並以文字加顏色區分，不可只靠顏色） |
| AC-1.3 | 輸入高風險特徵（月繳合約、tenure=1、Fiber optic、Electronic check、MonthlyCharges=100） | 按「預測」 | 風險等級為「高」 |
| AC-1.4 | 輸入低風險特徵（兩年合約、tenure=70、自動扣款、MonthlyCharges=30） | 按「預測」 | 風險等級為「低」 |
| AC-1.5 | PhoneService 選「No」 | 查看 MultipleLines | 該欄位自動固定為「No phone service」且不可改（與資料集一致） |
| AC-1.6 | InternetService 選「No」 | 查看 6 個網路附加服務欄位（OnlineSecurity、OnlineBackup、DeviceProtection、TechSupport、StreamingTV、StreamingMovies） | 皆自動固定為「No internet service」且不可改 |
| AC-1.7（Q3 修改；2026-11-20 修改） | 18 個必填欄位未填，或 tenure 不在 0 至 72 的整數、MonthlyCharges 不在 0 至 200、或 TotalCharges 有填但為負數或非數字，或 TotalCharges 留空但估算值（tenure x MonthlyCharges，四捨五入到 2 位小數）> 10,000 | 按「預測」 | 前端不送出，並在對應欄位旁顯示具體錯誤訊息（如「在網月數需為 0 至 72 的整數」）；估算值超過上限時，TotalCharges 欄位下顯示「估算累計費用超過上限，請手動填寫」。TotalCharges 留空一般不算錯誤，唯一例外是估算值 > 10,000 |
| AC-1.14（Q3 新增） | TotalCharges 留空，tenure=10、MonthlyCharges=50 | 按「預測」 | 可成功預測；結果區註明「累計費用以 500 估算」（10 x 50）；與手動填入 TotalCharges=500 的預測機率完全相同 |
| AC-1.15（Q3 新增） | TotalCharges 有填（如 1200） | 按「預測」 | 使用填入的值預測，不顯示「估算」註記 |
| AC-1.16（Q3 新增；2026-11-20 修改） | 直接呼叫預測 API，不帶 TotalCharges 欄位（或值為 null） | 送出請求 | 回 200 並成功預測，回應中標明累計費用為估算值；例外：估算值（四捨五入到 2 位小數後）> 10,000 時回 422，錯誤指出欄位為 TotalCharges；帶入非法值（負數、字串）同樣回 422 |
| AC-1.17（2026-11-20 新增） | 手填 TotalCharges=1200.005（或留空且 tenure x MonthlyCharges 產生第 3 位小數的 5，如 tenure=1、MonthlyCharges=20.005） | 呼叫預測 API | 以 half-up 四捨五入到 2 位小數後預測；回應的 total_charges.value 為實際用於預測的值（1200.005 回 1200.01；20.005 回 20.01） |
| AC-1.8 | 直接呼叫預測 API 並傳入非法值（未知類別、缺欄位、字串當數字） | 送出請求 | 回傳 HTTP 422，內容指出哪個欄位錯在哪裡；服務不當機，且不回傳預測值 |
| AC-1.9 | 後端服務停止或模型檔缺失 | 按「預測」 | 畫面顯示「服務暫時無法使用」類的友善訊息與重試按鈕，不顯示空白頁或原始錯誤堆疊；API 在模型缺失時回 503 |
| AC-1.10 | 預測進行中 | 等待回應 | 「預測」按鈕變為不可按（防重複送出）並顯示載入狀態；回應後恢復 |
| AC-1.11 | 同一組輸入連續預測 2 次 | 比較結果 | 機率完全相同（推論結果確定，不隨機） |
| AC-1.12 | 單筆預測 API 在本機 Docker 環境、模型已載入 | 連續 50 次請求 | p95 回應時間 < 500 毫秒（不含服務啟動） |
| AC-1.13 | 預測結果顯示後 | 查看結果區 | 有一行固定提示：「模型以公開範例資料訓練，僅供展示，不可用於真實決策」 |

### F2 影響此預測的主要因素

**US-2** 身為留客分析人員，我想要知道「是哪些因素讓這位顧客風險偏高或偏低」，以便知道該對他採取什麼行動，也能信任模型不是黑盒子。

| 編號 | Given | When | Then |
|---|---|---|---|
| AC-2.1 | 已完成一筆預測 | 查看結果 | 顯示影響最大的前 5 個因素，依影響程度由大到小排序 |
| AC-2.2 | 查看每個因素 | 閱讀內容 | 每項包含：因素名稱（中文可讀，如「合約類型：月繳」，不可出現 `Contract_Month-to-month` 這類內部欄位名）、方向（推高風險／拉低風險，文字加圖示）、相對影響大小（長條圖或數值） |
| AC-2.3 | 比較 AC-1.3 與 AC-1.4 兩組輸入 | 查看主要因素 | 兩組的因素清單不同，且 AC-1.3 的因素中「合約類型：月繳」為推高風險、AC-1.4 的「合約類型：兩年約」為拉低風險 |
| AC-2.4 | 連續預測同一組輸入 2 次 | 比較因素清單 | 因素與順序完全一致 |
| AC-2.5 | 查看因素說明區 | 閱讀 | 有一句白話說明這些因素代表「模型的判斷依據」，不代表「真正的因果關係」 |
| AC-2.6 | 預測 API 回應 | 檢查內容 | 因素資料與機率在同一次回應中一併回傳（前端不需另外再呼叫才能顯示因素） |

| AC-5.9 | 查看 `docs/` 下的 ADR | 閱讀 | 至少 4 篇，每篇含：背景、選項、決定、後果。必須涵蓋：模型選擇、不平衡處理與指標選擇、TotalCharges 空值處理、是否使用資料庫 |
| AC-5.10 | 依 README 從零操作 | 另一位不熟專案的人照做 | 能在 15 分鐘內（不含下載資料與 Docker 映像檔下載時間）完成啟動並預測成功 |

### F6 批次上傳 CSV 預測

**US-6** 身為留客分析人員，我想要一次上傳一份顧客名單，以便得到每位顧客的流失風險並找出最需要優先處理的人。

輸入格式：CSV，欄位同 F1 的輸入欄位（18 個必填；TotalCharges 欄位可整欄省略，或個別列留空，皆比照 F1 以 tenure x MonthlyCharges 估算）；可選填 `customerID` 欄位，有的話原樣帶回結果以便對照。提供範本 CSV 下載。

| 編號 | Given | When | Then |
|---|---|---|---|
| AC-6.1 | 頁面有「下載範本 CSV」 | 點擊 | 下載含正確欄位標題與至少 2 列範例資料的檔案，且該檔案直接上傳能預測成功 |
| AC-6.2 | 上傳 100 筆合法 CSV | 送出 | 顯示結果表格，每列含 customerID（若有）、流失機率、風險等級；預設依機率由高到低排序 |
| AC-6.3 | 結果表格 | 點擊風險等級篩選（低／中／高）或欄位排序 | 表格即時依條件過濾或排序 |
| AC-6.4 | 結果表格 | 點「下載結果 CSV」 | 下載檔案含原始欄位加上機率與風險等級，筆數與畫面一致；中文與特殊字元在 Excel 開啟不亂碼 |
| AC-6.5 | 上傳結果 | 查看摘要 | 顯示總筆數與低／中／高風險各幾筆 |
| AC-6.6 | 上傳非 CSV 檔、空檔，或缺少必要欄位 | 送出 | 顯示具體錯誤（如「缺少欄位：Contract、tenure」），不做任何預測 |
| AC-6.7 | CSV 中有部分列資料非法（如 tenure 為負數） | 送出 | 預設行為為整份拒絕，並列出有問題的列號與原因（最多列 20 筆，其餘顯示「另有 N 筆」）；不得靜默略過 |
| AC-6.8 | 檔案超過上限（5 MB 或 10,000 列） | 送出 | 被拒絕並顯示上限說明；不當機 |
| AC-6.9 | 上傳 1,000 筆合法資料，本機 Docker 環境 | 送出 | 10 秒內顯示結果 |
| AC-6.10 | 處理中 | 等待 | 顯示載入狀態，上傳按鈕不可重複按 |
| AC-6.11 | 上傳完成後 | 檢查伺服器 | 上傳的內容不被持久儲存（不寫入資料庫或長期保留的檔案） |
| AC-6.12 | 同一份檔案上傳 2 次 | 比較結果 | 兩次結果完全一致 |
| AC-6.13（Q3 新增） | 上傳的 CSV 沒有 TotalCharges 欄位，或部分列該欄為空 | 送出 | 預測成功；缺值的列以 tenure x MonthlyCharges 估算，結果表格標示哪些列為估算；不視為錯誤。（2026-11-20 修改）例外：估算值超過 10,000 的列視為不合法列，依 AC-6.7 處理（整份拒絕並列出列號與原因） |

## 6. 非功能需求

| 編號 | 類別 | 需求（可驗證） |
|---|---|---|
| NFR-1 | 模型成效門檻 | 在固定的測試集上，Keras 模型：ROC-AUC >= 0.82；流失類別 Recall >= 0.70（在選定決策門檻下，並同時回報 Precision）。此為最低門檻，達不到須在 ADR 說明原因，不可為達標而調整測試集 |
| NFR-2 | 與基準比較 | Keras 模型的 ROC-AUC 不得比邏輯迴歸基準低超過 0.01。若沒有明顯優勢，如實呈現並在 ADR 說明為何仍採用（或改採）哪個模型；不可隱藏比較結果。（註：此資料集上簡單模型常與神經網路表現接近，這本身是值得在面試中講的結論） |
| NFR-3 | 回應時間 | 單筆預測 p95 < 500 毫秒；批次 1,000 筆 < 10 秒；成效頁資料 API < 300 毫秒（皆為本機 Docker、模型已載入） |
| NFR-4 | 啟動時間 | `docker compose up` 後 60 秒內服務可用（不含首次 image 下載與 build） |
| NFR-5 | 可重現性 | 固定亂數種子、套件版本鎖定（有鎖定檔）；相同條件重訓 ROC-AUC 差距 <= 0.01；訓練需在一般筆電（無 GPU）10 分鐘內完成 |
| NFR-6 | 資料一致性 | 訓練與預測使用同一份前處理設定（含 TotalCharges 缺值的處理規則）；有測試證明：同一筆資料經訓練流程與經 API，得到相同的特徵向量 |
| NFR-7 | 錯誤處理 | 任何 API 錯誤皆回傳結構一致的 JSON（含錯誤代碼與人看得懂的訊息）；不洩漏程式路徑或堆疊 |
| NFR-8 | 安全與隱私 | 不儲存使用者輸入；CORS 只允許前端網址；上傳檔案大小與列數有上限；不含任何金鑰寫死在程式碼（若有設定用環境變數）。資料集為公開範例，無個資 |
| NFR-9 | 瀏覽器與裝置 | 最新版 Chrome、Edge、Safari；桌機（1280 像素）與手機（375 像素）版面皆可用 |
| NFR-10 | 無障礙（基本） | 風險等級與影響方向不只靠顏色；表單欄位有標籤；可僅用鍵盤完成預測 |
| NFR-11 | 程式品質 | 後端與前端皆有 lint 與格式化設定，CI 零錯誤；前端使用 TypeScript 嚴格模式；後端對外 API 的輸入輸出皆有明確型別定義 |
| NFR-12 | 介面語言 | 介面使用繁體中文；README 以中文為主並附英文摘要（Q5 決定） |
